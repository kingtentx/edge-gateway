# 遥测、存储与故障语义

## MQTT 消息与平台模式

协议为 MQTT 3.1.1，QoS 1，不保留（retain=false），Clean Session。离线队列由本地 SQLite 管理。当前支持 Generic、ThingsBoard、ThingsCloud、ThingsPanel、IoTSharp；默认 Generic 保持原有主题与消息结构。以下为 Generic 示例，设备和点位 ID 仅用于说明：

```json
{
  "schemaVersion": 1,
  "messageId": "d715df342acd468c900e8d1706611517c",
  "gatewayId": "edge-001",
  "timestamp": "2026-10-22T10:00:00+00:00",
  "samples": [
    {
      "deviceId": "11111111-1111-1111-1111-111111111111",
      "deviceName": "演示机组",
      "tagId": "11111111-1111-1111-1111-111111111101",
      "tagName": "出水温度",
      "address": "sine",
      "rawValue": 50,
      "value": 40,
      "unit": "°C",
      "quality": "Good",
      "timestamp": "2026-10-22T09:59:59+00:00",
      "error": null
    }
  ]
}
```

外层 `timestamp` 是快照生成时间，点位 `timestamp` 是该次采集完成时间，均使用 UTC。云端应按点位时间判断新鲜度，按 `messageId` 去重，并保留质量；不要把 Bad 的 null 转成 0。

专用平台由 [PlatformMqttAdapter](../src/EdgeGateway.Service/PlatformMqttAdapter.cs) 生成对应主题和 JSON：ThingsBoard 使用 `v1/gateway/telemetry`，ThingsCloud 使用 `gateway/attributes`，ThingsPanel 使用 `gateway/telemetry`，IoTSharp 使用 `devices/{设备名称}/telemetry`。普通值字段只包含 Good 且非 null 的点位；`_edge` 元数据携带消息 ID、网关标识、生成时间、每点质量、原采样时间和错误。平台物模型须接纳该元数据，不可只读此前留下的普通值来判断当前质量。详细协议、认证与样例见 [平台接入与 RPC](platform-protocols.md)。

ThingsCloud 和 IoTSharp 将快照拆成每设备一条消息，同一快照共享消息 ID，接收端按设备标识与消息 ID 联合去重。Generic 消息仍为 `schemaVersion: 1`，本地 JSON 配置为 schema 2，SQLite 数据库亦独立维护自己的版本；三者不是同一个 schema。当前变更与执行状态见 [本轮记录](opc-ua-service-removal.md)，不沿用删除前版本的发布数量。

## 质量

| 质量 | 含义 |
|---|---|
| Good | 最近一轮真实成功采样且转换有效 |
| Bad | 读失败、缺失、非有限数值、协议异常；值置 null，带错误与失败时间 |
| Uncertain | 采集停止后的显示，或写入成功尚未读回；不可当作新成功数据 |

上报检查收集各点位最新样本，多个点位采集时间可能不同，不声称所有设备在同一物理时刻采样。历史存储各次采集结果；MQTT 按独立检查周期与报告策略选择最新值。倍率/偏移后有表达式时，表达式错误也生成 Bad，不因公式错误伪造有效值或反复重连本来正常的协议连接。

## 三种上报策略

“平台与系统”的上报模式作用于持久队列之前，检查周期仍为 `PublishIntervalMs`。默认 `Periodic`，旧配置保持周期上报。

| 模式 | 何时选择点位进入快照 |
|---|---|
| `Periodic` 周期全量 | 每个检查周期选取所有合格点位的最新样本 |
| `OnChange` 仅变化 | 初次值，或值超过死区，或质量/错误改变 |
| `OnChangeWithHeartbeat` 变化加心跳 | 满足变化条件，或距该点最后成功入队达到心跳间隔 |

`Deadband` 是最终工程量的非负绝对死区，数值相对上次成功入队的基线比较，小变化可累积后超过死区。布尔、文本、数组和对象按类型与内容比较，质量与错误改变独立触发；心跳间隔为 100–86400000 ms，不能短于检查周期。保留原采样时间，心跳不意味着设备重新读过一次。

基线只在该完整快照的全部平台消息成功持久化之后推进，不能在采样或发送尝试时提前改变。容量满或写库失败时以相同消息 ID 重试；分设备入队只完成一部分时，已落盘部分继续补传，未完成部分继续等待。中途配置改变则保留已入队片段，按新配置重建剩余选择，不把失败或未完成快照当作已保存。

进程启动、配置更新及设备会话重新启动会重新发送初值；其他设备持续运行时，仅重启 B 也不因旧死区基线抑制 B 的首帧。同一消息可能重复投递，接收端仍需幂等。实现见 [TelemetryReportPlanner](../src/EdgeGateway.Service/TelemetryReportPlanner.cs) 与 [入队流水线](../src/EdgeGateway.Service/GatewayRuntime.Telemetry.cs)。

这些模式都是最新值上报策略，不是完整采样事件日志。检查间隔内变化后恢复的瞬态值、队列回压期间未生成的中间快照不会逐条重建；完整采样记录应查询本地历史，并考虑历史落盘本身的故障边界。

## 上传范围与配置变化

生成新快照时捕获当前配置，只纳入 `DeviceConfiguration.Enabled` 为 true 的设备，以及其中 `Enabled` 与 `UploadEnabled` 均为 true 的点位，按设备 ID 和点位 ID 匹配最新样本。`UploadEnabled` 默认 true，旧 JSON 未包含该字段时保持原行为。

关闭上传不影响采集、实时显示和本地历史；修改运行设备的点位配置会按统一配置事务只重启该设备。手动停止但仍在配置中启用的设备，其旧样本标为 `Uncertain`，在其他设备维持共享上报任务时仍可能进入快照；点位时间戳和质量表示它不是新成功采样。禁用设备、禁用点位、关闭上传或删除配置会把相应点排除出后续新快照。

快照因容量满或持久化错误等待入队时，若配置已改变，会放弃尚未入队的旧快照并按新配置生成。配置切换不能撤回已经开始的一次入队操作：该次操作可能仍保存旧内容。**已经持久化的 outbox 保留原主题、原消息 ID 和原载荷继续补传**，不因关闭上传、停止或删除设备而清空。需要限制已有积压的投递时，应在应用前处理这些消息，不能把上传开关理解成队列撤回命令。

对应实现：[配置应用](../src/EdgeGateway.Service/GatewayRuntime.Configuration.cs)、[遥测与诊断](../src/EdgeGateway.Service/GatewayRuntime.Telemetry.cs)。操作入口与完整结果语义见 [运行中配置与数据闭环](live-configuration.md)。

## 队列与故障

| 情况 | 行为 |
|---|---|
| 设备掉线 | 生成 Bad 样本，独立退避；启用故障降速时按阈值调整重试间隔；等待时释放通道，其他设备继续 |
| 单点设备异常响应 | 该点 Bad；同设备其他可读点继续 |
| MQTT 离线/认证失败/超时 | 已入队消息保留；按退避周期重试 |
| 发送确认后删除前崩溃 | 该消息可能再次发送；接收端按设备/消息标识幂等 |
| 发送确认后删除失败 | 记录持久化/补传错误，保留记录后重试，可能重复确认同一消息 |
| ThingsCloud 注册或属性应用响应失败 | 不把 PUBACK 当作成功；保留原 outbox 并重试 |
| 队列达到容量 | 保留旧消息，当前快照等待入队；暂停生成后续快照并报警，配置变化后重建未入队快照 |
| 磁盘写入失败 | 明确记录写入失败；采集不中断，但该历史批次未保存 |
| 单设备停止或局部重配置 | 只结束目标会话；其他设备与共享上报继续，未确认队列保留 |
| 最后一台正常停止 | 取消采集与共享 MQTT/RPC 任务，等待已接受历史批次处理，关闭驱动，保留未确认队列 |
| 断电/进程强杀 | 已提交 SQLite 事务按数据库机制恢复；尚在内存中的采样/快照不保证保留 |
| 切换平台类型 | outbox 非空时在配置保存前拒绝；先使用原平台完成补传 |
| 同平台更换 Broker、连接或账号标识 | 有积压时界面要求明确确认是否迁移待传消息；取消则不保存。确认后旧主题/载荷通过新连接发送，建议先用原连接排空队列；运行时 API 不替调用方作此交互决定 |

SQLite `samples` 保存设备 ID、点位 ID、UTC 毫秒时间与完整样本 JSON，`outbox` 保存主题、消息体、生成时间和递增 ID。数据库 schema 2 新增 `rpc_commands` 持久命令占位与结果，保留已有样本和 outbox；命令记录不随历史保留周期删除。历史查询为 `From <= timestamp <= To`，按时间倒序返回，单次最多 10,000 条。

## 发送确认与通信诊断

发布器等待 QoS 1 PUBACK；ThingsCloud 还必须收到 `gateway/attributes/response` 的 `result=1` 才报告发送成功并删除 outbox。当前运行子设备的连接注册与属性发送在同一个 MQTT 互斥区内排序，注册也必须收到匹配地址的应用响应，不能只靠后台稍后补通知。

本地已停止或已删除设备的旧快照继续补传。ThingsBoard 遥测允许自动创建设备；ThingsCloud 先发送原载荷，若云端明确回复绑定不存在且配置了类型标识，则临时注册该历史路由、重发原消息并立即断开。样本时间和质量不改，也不在本地把该设备伪装成运行。缺少云端绑定且无法注册时明确保留积压，需恢复云端配置。ThingsCloud 实时属性补传仍走原主题，原采样时间位于 `_edge`；平台按到达时间执行的规则须自行处理旧值，未将既存消息改写为历史 series API。

PUBACK 仅说明 Broker 确认；ThingsCloud 属性成功响应进一步说明对应平台 API 接受。**两者均不证明所有下游规则、消费去重或业务入库完成。** 确认后删除前中断、确认丢失或删除失败仍可能重发，因此保留至少一次语义。平台协议依据与具体限制见 [平台协议说明](platform-protocols.md)。

“通信诊断”页使用“最近/累计发送确认”，同时显示任务、连接、入队、发送尝试、待补传数量与最早时间、连续失败、下次重试和错误。模型中的 `LastBrokerAcknowledgedAt` 名称为既有接口兼容保留，当前表示发布器按对应平台规则完成确认的时间。设备最近成功、失败、耗时与降速反映现场链路；设备统计按服务读写批次计数，不当作底层帧数。

`TelemetryPipelineStatus` 的计数和事件时间为进程内状态，局部设备重配置不会清空，程序重启后重新累计。累计确认可能多次包含同一消息，不是去重后的平台记录数。连续失败包括 outbox 读取、发布或确认移除失败，正常取消不计失败。发送错误与持久化错误分别显示，恢复清除当前错误但保留历史时间和日志。队列数量及最早时间来自持久存储。字段见 [诊断模型](../src/EdgeGateway.Model/TelemetryPipelineStatus.cs)。

## 远程点位 RPC

RPC 使用同一 MQTT 连接的真实订阅、入站有界队列和回复发送，不在 MQTT 回调里执行设备 I/O。默认 `RpcEnabled=false`、`AllowRemoteWrite=false`；只开放 `read`、`write`，校验设备/点位身份、启用与运行状态，写入还需 Writable 并在设备锁内重新检查远程权限。读命令主动采样，写命令复用一次写入与显式读回，只有 Matched 才报告成功。

远程写在执行前由 SQLite 事务占位，完成后持久化原始回复。同标识重复请求重放结果，内容或方法冲突拒绝；已有占位但结果不确定时返回 Indeterminate，不自动重复执行。读取缓存有界且不跨重启，写审计不静默清理；总量达到 10000 条时保留证据并拒绝新远程写。身份域、令牌轮换、处理上限、停止语义与示例统一见 [平台接入与 RPC](platform-protocols.md)。RPC 的执行成功、MQTT 回复送达及上位业务处理仍是不同阶段。

高低阈值目前以状态变化日志呈现，无独立告警确认/工单系统。通信失败不会被误报为阈值恢复；取得新的有效值后才重新判断阈值状态。
